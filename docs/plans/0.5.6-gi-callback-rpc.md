## Purpose

- **🔷** `⏳` New live RPC type in the same family as `Live.Remote` / `Live.Subscribe` — e.g. **`OLLMrpc.Live.Callback`** with wire prefix **`RPC-Live-Callback`**.
- **🔷** `⏳` Client calls **`RPC-Live-Callback.register`** and gets a **callback id** back; when the watch / binding is done, **`RPC-Live-Callback.unregister`** drops it.
- **🔷** `⏳` Typelib methods that take a GIR `CALLBACK` send that **id** on the wire (a number), not a C function pointer.
- **🔷** `⏳` Server installs a fixed trampoline; on each mutter invoke, the client is told about the event via **`Notification`**.
- **🔷** `⏳` Client demux looks up the id and **fires the registered handler**.
- **🔷** `⏳` **Notification reply** — today’s `Notification` has **no answer** (no matching `Response`). Callbacks that return a value (and any invoke that must acknowledge) need a reply path. That feature lives on **`Live.Callback`** (or on `Notification` used only for callbacks): server invoke → client handler → **reply** with packed return / void ack. Not a side note for “later foreach”.
- **🔷** `⏳` Same `live_handles` flag / `Request.register("RPC-Live-Callback", …)` boot wiring as the other Live types.
- **🔷** `⏳` Unregister ends the story: client after `remove_watch` / `remove_keybinding`, **and** server `DestroyNotify` when mutter frees the trampoline `user_data`.
- **🚫** Do not invent Meta APIs. Do not noop shell-used keybinding / idle APIs.
- **🚫** Do not leave void callbacks as the only design — design reply into `Live.Callback` from the start (B2 may reply empty; B3 replies `bool`).

## Model (one picture)

```
client: RPC-Live-Callback.register  →  callback_id
        (client table: id → local delegate)

client: add_idle_watch(..., callback_id, ...)
        // wire: uint where GIR has CALLBACK

server: Gi.convert(CALLBACK) → trampoline + user_data = { connection, id }
mutter: idle / foreach / key → trampoline(..., user_data)
server: Notification {
          method = "RPC-Live-Callback.invoke",
          id     = callback_id,   // callback id (and/or correlation)
          args   = …
        }

client: notification → run registered delegate
client: Live.Callback.reply(correlation, return_args…)
        // void handlers: empty / ack reply
        // WindowForeachFunc: args("b", continue)

server: trampoline waits for reply (where GIR return matters) → returns to mutter

// done
client: remove_watch → RPC-Live-Callback.unregister(callback_id)
  — or —
mutter: DestroyNotify → server drops row (+ optional forget notify)
```

**ℹ️** Stock `Notification` today: push only, no `Response` id. Signal subscribe stays fire-and-forget. Callback invoke is the first live path that **needs** an answer.

Parallel to today:

| Live type | Register how | Server → client | Client → server |
| --- | --- | --- | --- |
| `RPC-Live-Remote` | ref / unref | — | — |
| `RPC-Live-Subscribe` | `signal` / `unsubscribe` | `Notification` (no reply) | — |
| **`RPC-Live-Callback`** | **`register` / `unregister`** | `Notification` **invoke** | **`reply`** (return / ack) |

**Lifecycle:** register → use (typelib + invoke + **reply**) → unregister.

## Notification reply (important)

**🔷** `⏳` `Live.Callback` owns the answer feature:

- Server tags each invoke with a **correlation** (request-style id on the notification, or a field on `Notification` used only for this path).
- Client runs the handler, then calls something like **`RPC-Live-Callback.reply`** (or `notif.reply(...)` helper on the Callback API) with packed return values.
- Server trampoline completes the GI callback with that return (or void).

**🔷** `⏳` Void Meta callbacks (idle watch, key handler) still go through the same path — reply is empty / ack — so one mechanism covers B1/B2/B3.

**🚫** Do not invent a second push channel beside `Notification` for the invoke itself. **🔷** Extend how invoke is answered, not how it is delivered.

**ℹ️** Exact API shape (`Notification` gains a reply id vs Callback-only `reply` RPC) is decided in OPC [`8.3.6`](file:///home/alan/gitlive/OLLMchat/docs/plans/8.3.6-rpc-live-callbacks.md) — must be written as requirements there, not as optional asides.

### B2 — IdleMonitor (first smoke)

**Shell** (`unlockDialog.js` / `screenShield.js`):

```js
this._idleWatchId = this._idleMonitor.add_idle_watch(HINT_TIMEOUT * 1000, () => {
    this._hint.ease({ opacity: 255, duration: CROSSFADE_TIME });
});

this._becameActiveId = this.idleMonitor.add_user_active_watch(
    this._onUserBecameActive.bind(this));
```

**Generated stub today:**

```vala
public uint32 add_idle_watch(uint64 interval_msec, IdleMonitorWatchFunc callback,
		void user_data, GLib.DestroyNotify notify) {
	GLib.error("gi-stub: Meta-IdleMonitor.add_idle_watch not wired");
}

public delegate void IdleMonitorWatchFunc(IdleMonitor monitor, uint32 watch_id, void user_data);
```

**Target stub shape (sketch):**

```vala
public uint32 add_idle_watch(uint64 interval_msec, IdleMonitorWatchFunc callback, ...) {
	var id = Runtime.callback_register(callback);  // → RPC-Live-Callback.register
	var response = Runtime.call_values(
		"Meta-IdleMonitor.add_idle_watch", this,
		OLLMrpc.args("tt", interval_msec, id));  // CALLBACK → id
	return (uint32) response.args.get(0).get_uint();
}
```

Notify payload: monitor lease + `watch_id` (no Clutter). Client `RPC-Live-Callback.invoke` demux calls the stored `IdleMonitorWatchFunc`.
