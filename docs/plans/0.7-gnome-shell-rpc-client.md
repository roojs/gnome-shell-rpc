# 0.7 — `gnome-shell-rpc-client` (meson in gnome-shell vs vendor here)

Checklist: `docs/guide-to-writing-plans.md`.

**Status:** **PROPOSED**

**Parent:** [`0.6-libmutter-rpc.md`](0.6-libmutter-rpc.md)

**Depends on:** 0.6 Phases 1–3 (`libmutter-rpc-16` + GJS actually `dlopen`s it). Spawn polarity: [`0.4-server-spawns-shell-client.md`](0.4-server-spawns-shell-client.md) (placeholder; this plan names the child).

**Target distro (nested):** gnome-shell **48** / Meta-**16**. Sibling git gnome-shell (API 51) is not the first binary.

---

## Agent rule: do not change the user’s session

Same as **0.1** / **0.6** — nested tests only. **🚫** replace host `/usr/bin/gnome-shell`. **🚫** `meson install` over the live session.

---

## Purpose

0.6 is the **library** (mutter-shaped client `.so` + typelib). This plan is the **process** GJS runs in: an executable **`gnome-shell-rpc-client`** that does **not** start a compositor, loads gnome-shell JS, and talks Meta via `libmutter-rpc`.

**🔷** `⏳` **`gnome-shell-rpc`** (mutter plugin, this repo) **boots that client** after the RPC socket is up — same polarity as [0.4](0.4-server-spawns-shell-client.md) (today it spawns `gjs-embed` + a smoke). Stock `/usr/bin/gnome-shell` stays the in-process compositor for people who are not using the split.

**🔷** Two places the client binary can be **built**. Pick one for the first nested boot; the other can still be the distro endgame.

```
mutter --mutter-plugin gnome-shell-rpc.so
        │  listen RPC
        │  spawn ──────────────────────────────┐
        ▼                                      ▼
  compositor (real libmutter)         gnome-shell-rpc-client
                                        GJS + js/ui
                                        libmutter-rpc-16  (Meta-16.typelib)
```

---

## What the binary is (and is not)

| | |
| --- | --- |
| **Is** | A **second** executable: GJS host + gnome-shell JS + `GI_TYPELIB_PATH` / link to **libmutter-rpc**. Connect-only to the plugin. |
| **Is not** | A rename of stock `gnome-shell` / `main.c` that still `meta_context_start()`s a compositor. |

**ℹ️** Stock `src/main.c` **is** mutter (it calls `meta_context_start` as compositor). Symbols can still match ([0.6](0.6-libmutter-rpc.md) **C API**). The new target needs a **client `main`** (this repo’s `gjs-embed` is the prototype) or a stripped `main.c` that never starts DRM — that is **behaviour**, not a header rewrite.

**🚫** Do not eval `js/ui/init.js` as the first nested proof. Same as 0.6 Phase 3: `Shell` / `St` / `global` / stage are later. First client boot = existing smokes, then more JS, not full chrome.

## Option A — meson in the GNOME Shell repository

**🔷** `⏳` Add a meson target in **gnome-shell** that builds **`gnome-shell-rpc-client`**, installable **next to** `gnome-shell` (same prefix / bundle), **not** replacing it.

**Likely files (gnome-shell tree):**

| File | Role |
| --- | --- |
| `src/meson.build` | extra `executable('gnome-shell-rpc-client', …)` |
| new `src/rpc-client-main.c` (or similar) | GJS embed; **no** `meta_create_context` compositor path |
| `meson_options.txt` | e.g. `-Drpc_client=true` so default distro builds stay stock |

**Depends (gnome-shell meson):** `dependency('libmutter-rpc-16')` from **this** repo (pkg-config), plus existing `gjs-1.0`. JS still `gi.require('Meta', LIBMUTTER_API_VERSION)`.

**Add (this repo):** after listen, spawn **`gnome-shell-rpc-client`** with `MUTTER_RPC_SOCKET`, `WAYLAND_DISPLAY`, `GI_TYPELIB_PATH` (rpc typelib first). Replaces or sits beside today’s `gjs-embed` + `meta-smoke.js` spawn in `Rpc.Server`.

**ℹ️** “Part of the installable bundle” means the **gnome-shell package** ships two binaries: `gnome-shell` (today) and `gnome-shell-rpc-client` (split). Session / nested mutter picks the client via the plugin, not via replacing the session binary on day one.

**Cost:** two checkouts, two mesons; gnome-shell build needs libmutter-rpc **installed or in `PKG_CONFIG_PATH`**. Upstream gnome-shell will not take this until the split is real — first landing is a **local** gnome-shell 48 branch / patch.

## Option B — vendor gnome-shell in this project

**🔷** `⏳` This repo’s meson builds **`gnome-shell-rpc-client`** from **gnome-shell sources** kept here (submodule, `meson wrap`, or a pinned checkout). Nested: one `ninja`, plugin already knows `bindir`.

**Add:** e.g. `subprojects/gnome-shell` (or `vendor/gnome-shell`) **pinned to 48.x** to match `libmutter-16`. Build the **client** target only — **🚫** do not build stock `gnome-shell` / mutter plugin from that tree inside nested tests.

**Use from that tree:** `js/` (and whatever `gjs-embed` needs for search-path / resources). Compiling `libst` / `libshell` against **stock `meta/*.h`** + **`-lmutter-rpc-16`** is the [0.6](0.6-libmutter-rpc.md) C path — not a forbidden ABI. Stock `main.c` still must not start a compositor in this process.

**Cost:** tree size, 48-vs-51 drift vs `/home/alan/git/gnome-shell`, keep the pin explicit.

---

## A vs B (facts, then a suggestion)

| | **A** meson in gnome-shell | **B** vendor here |
| --- | --- | --- |
| Who **compiles** `gnome-shell-rpc-client` | gnome-shell meson | this repo meson |
| Who **installs** it | gnome-shell prefix / distro package | this repo prefix / nested `bindir` |
| Who **starts** it | **this** plugin (both) | **this** plugin (both) |
| Nested iterate | two builds; pc must find libmutter-rpc | one tree (plugin already spawns `bindir`) |
| Distro story | extra binary in the shell package | extra binary from **this** project |
| First sources | need a client `main` in gnome-shell | already have `gjs-embed`; JS can come from vendor/`js` |

**💩** Suggested sequence (confirm before treating as 🔷): **B for the first nested boot** (vendor or wrap **`js/`**, binary **in this repo**, named `gnome-shell-rpc-client` — `gjs-embed` renamed/wrapped). **A when** libmutter-rpc is a real pc and the client `main` is stable enough to live as a gnome-shell meson option. Same spawn code either way.

**ℹ️** Vendoring **only `js/`** is not a third option in conflict with A/B — it is **B light**: this repo still produces the executable; gnome-shell git is the JS source, not a second compositor meson.

## Spawn (plugin → client)

**🔷** `⏳` Polarities stay [0.4](0.4-server-spawns-shell-client.md): server listens, then starts the client. Client is connect-only (no `ClientBoot`).

**ℹ️** Today `Rpc.Server` already `Meta.WaylandClient.spawnv`s `gjs-embed` + a smoke, with `GI_TYPELIB_PATH` prepended.

**Remove:** smoke-only argv as the **product** spawn (keep it behind the existing smoke env for tests).

**Replace with:** argv `gnome-shell-rpc-client` (path: `bindir` for B; `pkglibdir`/`bindir` from gnome-shell prefix for A) + the same socket / Wayland / typelib env.

**🚫** Do not spawn stock `gnome-shell`. **🚫** Do not `kill` host gnome-shell to “test respawn.”

## Out of scope

- **🚫** Full `js/ui/main.js` / St-on-stage as this plan’s exit.
- **🚫** Replacing the user’s session `gnome-shell` binary.
- **🚫** Full St-on-stage as this plan’s exit (runtime chrome, not “C names cannot match”).
- **🚫** Expanding 0.4’s respawn/backoff policy here — pointer only.

---

## Suggested order

1. **🔷** 0.6 library exists and GJS smokes `dlopen` it.
2. **🔷** Name the host **`gnome-shell-rpc-client`** (even if it is still `gjs-embed` guts).
3. **🔷** User picks **A** vs **B** (or **B light** then **A**).
4. **🔷** Plugin spawn points at that binary ([0.4](0.4-server-spawns-shell-client.md)).
5. **⏳** Nested: compositor only → client appears (smoke JS first, not `init.js`).

---

## Exit

- **⏳** A binary named **`gnome-shell-rpc-client`** exists (this repo and/or gnome-shell meson).
- **⏳** Nested plugin **starts it**; it is not the compositor.
- **⏳** User **✅** A vs B (or the B-then-A sequence).
- **⏳** Full gnome-shell JS chrome still **not** required.

## Open questions
