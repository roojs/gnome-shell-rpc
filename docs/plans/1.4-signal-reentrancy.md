# 1.4 — A click must finish before the next frame

**User goal:** a click handler in the shell must finish before an unrelated frame update runs, the same way it does in stock GNOME Shell. A call that handler makes, and a signal that call itself causes, still run straight away.

**Status:** ✔️ implemented. `event-reschedule` passes stage 5, the reviewed
stage 6 change is applied, and the installed-guest check remains.

Procedure: [`docs/debugging.md`](../debugging.md). A product-code proposal is

## Purpose

- 🔷 The shell and the compositor are two processes. A click still has to run as one uninterrupted piece of work.
- 🔷 Work started by the click handler runs now.
- 🔷 Work that only became ready while the click was running waits until the click has finished.
- 🔷 How to prove a reentrancy change, and how to name a result, is [`docs/signal-reentrancy.md`](../signal-reentrancy.md). This plan follows that. Testing stays in `tests/call-sync-repro/signal-reentrancy-gate.vala`.
- 🔷 Resolve the ordering rule in the stand-alone suite before proposing any change under `src/`.

## What a normal click does

1. The compositor takes the next pointer event.
2. Clutter emits `clicked`.
3. The shell runs the first `clicked` handler.
4. That handler calls Mutter and waits for the call to return.
5. Mutter returns.
6. The shell runs the other `clicked` handlers.
7. `clicked` returns to Clutter.
8. The compositor goes back to its main loop.
9. Only then may a frame update emit `before-update`.

- 🔷 `before-update` must not run between steps 3 and 6 just because a frame became ready.
- 🔷 A signal emitted by the Mutter call in step 4 is part of that call. It runs before the call returns.

## The same click across the two processes

1. The server takes the pointer event and starts this click.
2. The server sends `clicked` to the shell and waits until the shell finishes it.
3. The shell runs the first `clicked` handler.
4. The handler calls back to the server, still inside this click.
5. The server does that call and replies.
6. The shell finishes the first handler, then runs the other `clicked` handlers.
7. The shell tells the server the signal is finished.
   - A boolean signal includes the handler result.
   - A void signal is only "finished".
8. The server ends the click.
9. The server may now run the next waiting piece of work, including `before-update`.

- 🔷 The bug is step 9 happening between steps 4 and 6.
- ✔️ Existing failure: `current` prints `FAIL current: before-update started drag inside clicked`.

## What the code does today

- ✔️ `clicked` starts, and the first handler calls the server and waits in `client.call_poll()`.
- 🚫 During that wait, `before-update` arrives and runs.
- 🚫 `Meta.Laters.run_before_redraw()` then runs the drag callback before the second `clicked` handler sets `_actionClicked`.
- ℹ️ `Meta.Laters.redraw_depth` only stops one drag callback from calling another. During this failure it is zero. The outer work is a signal, not a drag callback.
- ℹ️ A normal `before-update` is one signal deep. A signal delivered inside another signal is deeper than one. An earlier try treated "any signal is active" as nested, and that also matched `before-update` itself.

## Signals the server currently waits for

- 🔷 Stock GNOME Shell runs every connected handler before `g_signal_emit()` returns.
- ℹ️ This project waits only for the signal names listed in `src/server/libmutter-clutter-16/ClutterActor.vala`:
  - `button-press-event`
  - `button-release-event`
  - `captured-event`
  - `clicked`
  - `enter-event`
  - `event`
  - `key-press-event`
  - `key-release-event`
  - `leave-event`
  - `motion-event`
  - `scroll-event`
  - `touch-event`
  - `long-press`
- ℹ️ For those names the server waits for `RPC-Live-Callback.reply`, so Clutter gets the handler result before the signal returns.
- ℹ️ Every other signal is sent and not waited for. That is a shortcut. Stock Shell does not do that.
- ℹ️ Waiting for a reply does not by itself keep order. A waited-for signal can still arrive in the middle of another signal, inside `call_poll()`.
- 🔷 Every relayed signal should wait until its handlers finish.
  - A boolean signal sends back the handler result.
  - A void signal sends back "finished".
  - The wait is the same either way.
- ✔️ The `server` gate proves that boolean and void signals can use the same wait and differ only in reply payload.

## Stage 5 — resolve the rule in the stand-alone test

- ✔️ Holding a frame only while a relayed signal is open passes `server`.
- 🚫 That rule does not resolve the reproduced guest order.
  - `long-press` has already replied.
  - `before-update` arrives before `clicked`.
  - `server-gap` therefore remains an expected failure.
- ✔️ Holding from `long-press` until `clicked` passes the click arm in `event`.
- 🚫 That rule loses the frame when a drag has no `clicked`; `event-no-click` is the expected failure.
- ✔️ `event-scope` currently covers the remaining required order in the reproduction.
  - A frame waits while the pointer event is open.
  - The click arm releases it after `clicked` replies.
  - The drag arm releases it even though `clicked` never runs.
  - Frames arriving before `clicked` and during its nested call both wait.
  - A signal caused by the click's nested call still runs before that call returns.
  - Boolean and void signal completion use the same order.
  - A later frame with no event open runs immediately.
- ✔️ This rule now satisfies stage 5. It is not product code.
- ✔️ `event-reschedule` also satisfies the order without retaining frame arguments.
  - Frames that become ready during the pointer event request one follow-up frame.
  - Two arrivals before the event ends coalesce into that one follow-up.
  - The follow-up runs after `clicked`, or after a drag event with no `clicked`.
  - A later idle frame still runs immediately.
- ✔️ `clutter-event-frame-order-gate` proves the stock boundary.
  - `long-press(CANCEL)` and both `clicked` handlers have a current event.
  - `before-update` runs after both handlers and has no current event.
- 🔷 `event-reschedule` is the stage 5 result to carry into stage 6.

## Earlier test ideas

- ℹ️ These change when a frame update is delivered. They remain regression comparisons, not product proposals.

### Skip the drag callback when a frame update arrives inside another signal

- 💩 Count how deep `Signals.emit()` is, in `Gsr.Client.Rpc`, so `Meta.Laters` can read it without depending on `libshell`.
- 💩 Depth 1 is a normal `before-update`. Run the drag callback.
- 💩 Depth greater than 1 means this frame update arrived inside another signal.
  - Do not run `BEFORE_REDRAW` callbacks.
  - Ask for another frame.
  - Let the next top-level `before-update` run them.
- 🔷 Keep `redraw_depth`. It protects drag callbacks. The new depth protects signals. They are different.
- ℹ️ Smallest change, and it sits on the frame path this bug already shows.
- ℹ️ Replies, and callbacks the server is waiting for, still run immediately.
- ℹ️ Risk: the drag callback may run on a later frame than the one that was ready.
- ℹ️ Risk: nested frame updates must not postpone the callback forever.
- ℹ️ An earlier try postponed the callback whenever any signal was active. That also matched `before-update` itself. The check has to be "deeper than 1", not "deeper than 0".

### Hold the frame update until the click handler returns

- 💩 While `Signals.emit()` is still running, remember a `before-update` that does not need a return value.
  - Do not emit it yet.
  - Keep waiting for the server's reply.
- 💩 When the outermost signal returns, emit the remembered `before-update` in the order it arrived, then return the click result.
- ℹ️ This keeps the frame update that already arrived, instead of asking for another frame.
- ℹ️ Risk: the queued frame and object arguments must still be valid when they are delivered.
- ℹ️ Risk: delivering the queue may enqueue more updates, so the drain needs a bound and a stable order.
- 🔷 A nested signal whose result the server is waiting for cannot be queued. Queueing it can deadlock the call that caused it.

### Hold unexpected signals in the client until the current call returns

- 💩 While the shell is inside a synchronous call, `call_poll()` still accepts:
  - the reply to that call
  - nested callbacks the server needs before it can reply
- 💩 It holds other incoming signals until that call has returned.
- 🔷 Only a signal that does not need a return value may be held.
- ℹ️ One rule then covers more than `before-update`.
- ℹ️ `Shell.Signals` and `Meta.Laters` do not need to know which signal it is.
- ℹ️ Risk: this changes delivery for every notification.
- ℹ️ Risk: sorting replies, callbacks, and notifications may belong in libocrpc.
- ℹ️ If the change belongs in libocrpc, add a failing test under `tests/call-sync-repro/` and stop. Do not edit OLLMchat from this tree.
- ℹ️ Try this only after the smaller ideas above are shown to be insufficient.

### Open-signal server mode

- ✔️ Desired pass: `server-bool` and `server-void` print `PASS ... server sent the caused signal at once and held the ready frame`.
  - While a signal is open, a frame update that becomes ready is held.
  - A signal emitted by the call the shell just made is sent at once, before that call returns.
  - After the signal has finished, the held frame update is sent.
  - A later frame update, with no signal open, is sent at once.
- ✔️ Desired pass: `server` prints `PASS server: boolean and void use the same server decision`.
- ✔️ `src/` was not changed.
- ℹ️ The server could tell the two arrivals apart in this test, because one is emitted by the call it is running and the other is only a frame that became ready. The later gap reproduction showed that this distinction alone is insufficient.

### Stage 5 — compare candidate rules in the stand-alone test

- ✔️ One of the three client ideas keeps the order. `emit-queue` passed. `call-hold` and `later-skip` did not, and those two checks are meant to keep failing.
- ✔️ Those two failures are not "remove the name list". `proposal-during` skips the hold while the server is inside the shell's call, so that frame is sent at once. `proposal-noreply` waits for a reply the client never sends. - ✔️ Existing failure: `server-gap` prints `FAIL server-gap: frame between long-press and clicked started the drag`. The passing server rule still sends the frame, because `long-press` has already finished and `clicked` has not started.

  - The server sends the caused signal and waits, then a frame during the call, then the call's reply, then another frame while the click is still open. It does not wait for either frame.
  - The client runs the caused signal at once.

  - Boolean and void completion still differ only by `Y` and `K`.

- ✔️ Desired failure: `event-no-click` prints `FAIL event-no-click: frame after long-press without clicked was never sent`. Starting a hold on `long-press` and releasing it only on `clicked` loses the frame when the user drags and `clicked` never fires.

## LLM notes

- 🚫 Do not reorder or patch stock `dnd.js` handlers.
- 🚫 Do not add a vendor-shell production override.
- 🚫 Do not stop waiting for `clicked`. The failure already happens while the server is waiting for that reply.
- 🚫 Do not delay every nested message. A callback the server is waiting for will deadlock if it is queued.
- 🚫 Do not use `GLib.Idle`, or a nested `MainContext.iteration()`, to drain signals.
- 🚫 Do not treat `redraw_depth` as proof that no outer signal is active.
- 🚫 Do not add a `libmutter-rpc` dependency on `libshell`.
- 🚫 Do not pile a failed idea on top of another workaround.
