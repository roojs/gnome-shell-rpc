# 1.4 — Signal reentrancy ordering

**User goal:** preserve stock GNOME Shell's effectively synchronous signal ordering across RPC, and evaluate safe solutions for nested signal delivery.

**Status:** proposed; solution not selected.

Checklist: [`docs/guide-to-writing-plans.md`](../guide-to-writing-plans.md). Any proposed Vala must follow [`docs/coding-standards.md`](../coding-standards.md).

## Purpose

- 🔷 A signal handler must observe the same run-to-completion ordering as core GNOME Shell.
- 🔷 The server and client must behave as one logical call stack despite running in separate processes.
- 🔷 The plan must address signal reentrancy rather than patching the overview click symptom.
- 🔷 The options must account for synchronous nested RPC and blocking callback replies.
- 🔷 ⏳ Select and prove one ordering model before writing an implementation proposal.
- ℹ️ Investigation and reproduction: [`docs/bugs/2026-10-12-overview-thumbnail-drag.md`](../bugs/2026-10-12-overview-thumbnail-drag.md).
- ℹ️ Regression gate: `tests/gjs-embed/overview-window-activate-smoke.js`.
- ✔️ Off-code ordering gate: `tests/call-sync-repro/signal-reentrancy-gate.vala`.
- ✔️ RPC regression suite: `meson test -C build --suite signal-reentrancy --print-errorlogs`.

## Top-level execution model

- 🔷 GNOME Shell behaves as one logical thread with one active call stack.
- 🔷 The distinction is causality, not whether work originated on the server or client.
  - Work called by the active handler is nested work and runs on that stack.
  - Work from an independent event source is new top-level work and waits for the stack to unwind.
- 🔷 Only new top-level work is queued.
- 🔷 Nested calls and their replies must continue immediately or the active stack cannot finish.

### Stock click turn

1. The compositor dequeues a pointer event.
2. Clutter emits `clicked`.
3. GNOME Shell runs the first `clicked` handler.
4. That handler calls Mutter methods synchronously.
5. Mutter returns to the handler.
6. GNOME Shell runs the remaining `clicked` handlers.
7. `clicked` returns to Clutter.
8. The compositor returns to its main loop.
9. The next ready top-level source, such as a frame update, may now emit `before-update`.

- 🔷 `before-update` may not run between steps 3 and 6 merely because the frame source became ready.
- 🔷 A signal synchronously emitted by the Mutter method in step 4 is different:
  - it is caused by the active call;
  - it runs as a legitimate nested signal before the Mutter method returns.

### Equivalent RPC click turn

1. The server dequeues the pointer event and opens the logical turn.
2. The server relays `clicked` as a synchronous remote signal call.
3. The client runs the first `clicked` handler.
4. The handler sends a nested Mutter RPC on the same logical turn.
5. The server executes that nested call and sends its response.
6. The client resumes the handler and then runs the remaining `clicked` handlers.
7. The client sends signal completion, including a return value when the signal has one.
8. The server completes the original Clutter signal and closes the logical turn.
9. The server may now dispatch the next queued top-level source, including `before-update`.

- 🔷 The current bug is step 9 occurring between steps 4 and 6.
- 🔷 Nested RPC requests, responses, and causally nested signals are not put behind the top-level queue.
- 🔷 Independent input, frame, timer, and other main-loop sources are top-level work and cannot overtake the active turn.

### Client-originated work

- 🔷 A client RPC made by a handler is nested work on the active turn.
- 🔷 A client action from an independent client main-loop source starts a new top-level turn when no turn is active.
- 🔷 Origin does not decide priority.
  - Causally nested work runs now.
  - Independent work waits.

### What replaces the blocking list

- 🔷 The target is not another signal-name list.
- 💩 Every relayed GObject signal is a synchronous remote call on the logical turn.
- 💩 Signal completion is always returned:
  - boolean signals return the handler result;
  - void signals return completion only.
- 💩 The scheduler queues new top-level turns, not selected signal names.
- 💩 The current blocking list can be removed only after this generic turn behavior passes the full gate set.

## Current behaviour

- ✔️ `Signals.emit(clickAction, "clicked", ...)` begins synchronously.
- ✔️ The first JavaScript handler calls synchronous RPC through `Gsr.Client.Rpc.call_value()` and `client.call_poll()`.
- 🚫 `call_poll()` dispatches an incoming `before-update` notification before the first handler returns.
- 🚫 The notification causes nested `Signals.emit(stage, "before-update", ...)`.
- 🚫 `Meta.Laters.run_before_redraw()` runs the queued DND callback before the second `clicked` handler sets `_actionClicked`.

- ℹ️ `Meta.Laters.redraw_depth` guards only a later callback re-entering another later callback.
- ℹ️ It does not represent an outer signal emission.
- ℹ️ During the failing nested `before-update`, `redraw_depth` is zero.

- ℹ️ A normal `before-update` is itself one `Signals.emit()` deep.
- ℹ️ Any signal-depth solution must distinguish:
  - depth `1`: ordinary top-level signal delivery;
  - depth greater than `1`: a signal delivered inside another signal.

## Required ordering contract

- 🔷 A local GLib signal emission runs all connected handlers before a frame-boundary notification can overtake it.
- 🔷 Synchronous RPC responses must still be processed while a signal handler is active.
- 🔷 Nested blocking callbacks that are required to complete the current RPC must still be serviced.
- 🔷 A relayed frame signal may not execute shell JavaScript inside an unrelated outer signal.
- 🔷 Preserve the existing `redraw_depth` contract: a later callback may not be recursively invoked by a nested `before-update`.
- 🔷 The design may not add a `libmutter-rpc` dependency on `libshell`.
- 🔷 A failed candidate is reverted; it is not accumulated with another workaround.

## Stock signal contract and current wire policy

- 🔷 Stock GNOME Shell's GObject signals are synchronous.
  - `g_signal_emit()` invokes the connected handlers before it returns.
  - Stock Shell has no equivalent of an RPC `Notification` that independently arrives as blocking or non-blocking.
- ℹ️ `Notification`, `reply_id`, and `Subscription.blocking` are RPC transport concepts introduced by this project.
- ℹ️ The current hand list in `src/server/libmutter-clutter-16/ClutterActor.vala` contains:
  - `button-press-event`;
  - `button-release-event`;
  - `captured-event`;
  - `clicked`;
  - `enter-event`;
  - `event`;
  - `key-press-event`;
  - `key-release-event`;
  - `leave-event`;
  - `motion-event`;
  - `scroll-event`;
  - `touch-event`;
  - `long-press`.
- ℹ️ That list was introduced for boolean-return event signals.
  - The server waits for `RPC-Live-Callback.reply`.
  - Clutter receives the client's handler result before the server-side signal emission returns.
- ℹ️ Signals outside the list are currently relayed one-way.
  - That is an RPC optimization and semantic compromise.
  - It is not GNOME Shell's native signal model.
- ℹ️ `blocking` does not itself prevent client reentrancy.
  - A blocking signal can still arrive inside `call_poll()`.
  - Its client handler can still run inside another client signal.
- 🔷 Preserve synchronous handler completion for every relayed GObject signal.
- 🔷 Signal return type changes the reply payload, not scheduling semantics.
  - A boolean reply carries the handler result.
  - A void reply acknowledges handler completion.
- 🔷 Treat the hand list as transitional wire policy, not the target design.
- 💩 Replace the hand list with one generic synchronous signal-relay path after the distributed-call-stack gate passes.
- ✔️ Every pipe-policy mode receives a blocking callback first; the server withholds the synchronous response until the client replies.
- ℹ️ The current pipe gate protects nested callback progress, not a complete distributed call stack.
- 🔷 ⏳ Add an off-code distributed-call-stack gate before replacing the hand list.
  - Every relayed signal waits for client handler completion.
  - A handler may make a nested synchronous RPC.
  - A signal synchronously caused by that nested RPC may re-enter, matching an in-process C call.
  - An unrelated frame or event source may not overtake the active remote signal.
  - Boolean and void signals follow the same scheduling; only their reply payload differs.

## Proposed direction — one logical call stack

- 🔷 The RPC pair must behave as one logical GNOME Shell thread.
- 💩 A server-side signal relay opens a remote signal frame and waits for client handler completion.
- 💩 A client handler's synchronous RPC runs as a nested call on that frame.
- 💩 A signal synchronously emitted by that nested server call runs as a nested signal on the same frame.
- 💩 An unrelated server event source waits until the active remote signal frame closes.
- 💩 The client does not invent blocking and non-blocking signal semantics.
- 💩 `Subscription.blocking` becomes the generic signal-relay behavior.
- 💩 The hand-maintained signal-name list is then removed.

- ℹ️ This is the distributed equivalent of the in-process call stack.
- ℹ️ The transport still needs request, response, callback, and correlation messages.
- ℹ️ Those are implementation details; they do not create a second signal model.
- ℹ️ The unresolved implementation question is where to distinguish:
  - a signal caused synchronously by the nested RPC; from
  - an unrelated source that merely became ready while the remote signal was open.

## Fallback approximations

- ℹ️ Options 1–3 below alter scheduling at a consumer or transport boundary.
- ℹ️ They remain experiments for comparison, not the preferred semantic design.

## Option 1 — Guard frame-later dispatch with shared signal depth

- 💩 Record signal-emission depth in the neutral `Gsr.Client.Rpc` layer.
  - `Shell.Signals` increments it around `Signals.emit()`.
  - `Meta.Laters` reads it without depending on `libshell`.
- 💩 Treat depth `1` as an ordinary `before-update`.
- 💩 Treat depth greater than `1` as nested delivery.
  - Do not drain BEFORE_REDRAW callbacks in that nested emission.
  - Request another stage update.
  - Let the next top-level `before-update` drain the queue.
- 🔷 Keep `redraw_depth`; signal depth and later-dispatch depth protect different call stacks.

- ℹ️ Advantage: smallest change and limited to the frame-later boundary proven by the bug.
- ℹ️ Advantage: responses and blocking callback notifications remain in-flow.
- ℹ️ Risk: rescheduling changes which frame receives the callback.
- ℹ️ Risk: repeated nested frame notifications must not create a permanent reschedule loop.
- ℹ️ Prior failed attempt: checking whether any signal was active also matched the `before-update` signal itself.
- ℹ️ Required correction: distinguish nested depth greater than `1`, not active depth greater than `0`.

## Option 2 — Queue deferrable wire relays until the outer signal returns

- 💩 Track the outer `Signals.emit()` depth in `Shell.Signals`.
- 💩 When a nested return-independent `before-update` relay arrives:
  - retain its target and arguments;
  - return to `call_poll()` without emitting it;
  - continue waiting for the synchronous RPC response.
- 💩 When the outermost signal emission finishes:
  - emit the queued `before-update`;
  - preserve notification order;
  - then return the outer blocking callback result.

- ℹ️ Advantage: preserves the received frame notification instead of requesting another frame.
- ℹ️ Advantage: directly restores run-to-completion at the signal dispatcher.
- ℹ️ Risk: queued `Clutter.Frame` and object arguments must remain valid until delivery.
- ℹ️ Risk: the set of deferrable wire relays needs an explicit contract.
- ℹ️ Risk: draining queued signals may itself enqueue more notifications and needs a bounded, ordered drain.
- 🔷 Return-dependent nested signals cannot use this queue because the server may be waiting for their handler result.

## Option 3 — Serialize return-independent relays in the RPC client

- 💩 Change `client.call_poll()` integration so a synchronous call processes:
  - the matching response;
  - nested blocking invokes required for progress;
  - but queues unsolicited return-independent relays until the active client call stack unwinds.
- 🔷 Classify a relayed signal by its return contract before considering it deferrable.

- ℹ️ Advantage: one transport-level ordering rule covers signals beyond `before-update`.
- ℹ️ Advantage: `Shell.Signals` and `Meta.Laters` do not need event-specific knowledge.
- ℹ️ Risk: this changes delivery semantics for every RPC notification.
- ℹ️ Risk: response, invoke, and notification classification belongs partly to libocrpc.
- ℹ️ Risk: if the required change belongs to libocrpc, this repository must first provide a failing `tests/call-sync-repro/` gate and stop under the OPC rule.
- ℹ️ This option is architectural and should only follow evidence that the targeted consumer options are insufficient.

## Option 4 — Serialize remote signal frames on the server

- 💩 Use the server's active remote-signal frame as the scheduling boundary.
- 💩 Continue dispatching nested client RPC requests required by that frame.
- 💩 Relay signals synchronously caused by those nested requests as nested frames.
- 💩 Queue unrelated signal relays until the active remote-signal frame closes.

- ℹ️ Advantage: this is the closest option to one in-process call stack.
- ℹ️ Advantage: the client does not need a special case for `before-update`.
- ℹ️ Risk: causally nested and independently ready signals need an evidence-backed distinction.
- ℹ️ Risk: queuing the relay cannot alter the compositor's own frame-clock state.
- 💩 Test this option first after the distributed-call-stack gate names both signal classes.

## Rejected symptom fixes

- 🚫 Do not reorder or patch stock `dnd.js` handlers.
- 🚫 Do not add a vendor-shell production override.
- 🚫 Do not make `clicked` return-independent; the clean reproduction already fails while the server waits for its callback reply.
- 🚫 Do not defer every nested wire message; a queued return-dependent callback can deadlock the RPC that caused it.
- 🚫 Do not use `GLib.Idle` or a nested `MainContext.iteration()` as a signal drain.
- 🚫 Do not use `redraw_depth` alone as evidence that no outer signal is active.

## Evaluation

### Phase 1 — Prove the ordering boundary

- 🔷 ⏳ Keep `overview-window-activate-smoke` failing on `drag-on-click` before each product candidate.
- ✔️ `signal-reentrancy-gate current` reproduces the ordering failure over two pipes.
- ✔️ The server sends a blocking callback and waits for its reply before sending `before-update` and the synchronous response.
- ✔️ Every candidate mode services that blocking callback in-flow.
- ✔️ `later-depth`, `signal-queue`, `transport-queue`, and `server-delay` each preserve click run-to-completion in the isolated model.
- ✔️ `later-reentry` reproduces the original guard's call shape and proves the active later runs once, at callback depth one, followed by one deferred pass.
- ✔️ The suite also passes the existing response/invoke, nested call, nested notification, depth-two reply, same-hook re-entry, and relay-storm gates.
- ℹ️ The suite reports 12 passes, one expected baseline failure, no failures, and no timeouts.
- ℹ️ These passes prove each ordering policy is internally viable and preserve known RPC flows; they do not select a product layer or prove shell integration.

### Phase 2 — Build the distributed-call-stack gate

- 🔷 ⏳ Extend the pure-Vala pipe gate with one remote signal frame.
- 🔷 ⏳ Prove a nested synchronous RPC completes while that frame is open.

- 🔷 ⏳ Prove an unrelated signal source waits until the outer remote signal finishes.

### Phase 3 — Test server-side remote-frame serialization
