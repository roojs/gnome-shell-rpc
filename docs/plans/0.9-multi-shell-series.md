# 0.9 — Multi shell series (one package per Ubuntu release)

**User goal:** Keep one git tree. Ship a separate package for each Ubuntu release, built on GitHub, and test each package on a virtual machine for that release. Each package is the RPC stack for that release’s GNOME Shell (`libmutter-rpc-16` on 25.04, `libmutter-rpc-17` on 25.10, and so on).

**Status:** **proposed** (user 2026-10-29). Not started.

Checklist: [`docs/guide-to-writing-plans.md`](../guide-to-writing-plans.md). Proposed Vala follows [`docs/coding-standards.md`](../coding-standards.md).

**ℹ️** Packaging shape already decided in [`done/1.1-installable-bootable-session.md`](done/1.1-installable-bootable-session.md): one package name, `gnome-shell-rpc`, per distro release. Two generations are not installed side by side. `/usr/bin/gsr-server` stays one path.

## Purpose

- 🔷 Phases are one Ubuntu release each. The first phase is the Ubuntu 25.10 co-build.
- 🔷 Co-build means the GitHub Release still builds the Ubuntu 25.04 package, and also builds an Ubuntu 25.10 package.
- 🔷 Packages are built by the GitHub Release workflows and published on the `v*-packages` release.
- 🔷 A package is proven by installing it on a virtual machine whose Ubuntu release matches that package, and logging into the session.
- ⏳ Phase 1 is the 25.10 co-build. Phase 2 is 26.04. Phase 3 is 26.10.
- ℹ️ Today’s Release job is [`.github/workflows/x-debian.yml`](../../.github/workflows/x-debian.yml) in `ubuntu:25.04` with `ROOJS_APT_SUITE=plucky`. Publish is [`.github/workflows/release.yml`](../../.github/workflows/release.yml).

## Phase 1 — Ubuntu 25.10 co-build

**🔷** `⏳` GitHub builds a questing `.deb` next to the existing plucky `.deb`. The questing package links `libmutter-17` and vendors GNOME Shell 49. Install that `.deb` on a virtual machine that is Ubuntu 25.10 and log into the session.

- 🔷 `⏳` The 25.04 job stays. Container `ubuntu:25.04`, suite `plucky`, Shell 48, `libmutter-16`.
- 🔷 `⏳` A second Debian job builds on `ubuntu:25.10` for suite `questing`.
- 🔷 `⏳` One Release run produces both `.deb` files and, on a tag, publishes both on `v*-packages`.
- 🔷 `⏳` Prove on a virtual machine whose `lsb_release` is 25.10 and whose `gnome-shell --version` is 49. Install the questing package. Log into the GNOME Shell RPC session.
- ℹ️ `debian/control` Build-Depends and Depends are `libmutter-16-dev` and `gnome-shell` `>= 48` `<< 49`. `meson.build` requires `libmutter-16` `>= 48` `< 49`. [`gnome-shell/meson.build`](../../gnome-shell/meson.build) pins the vendor tree to `48.0` and errors on any other major.
- ℹ️ `apt-get build-dep ./` reads `debian/control` before `debian/rules` runs. The questing job has to change those bounds before `build-dep`.
- 💩 `⏳` Add a `workflow_call` input for the container image, `ROOJS_APT_SUITE`, and the artifact name. Defaults stay plucky. The questing call uses image `ubuntu:25.10`, suite `questing`, artifact `gnome-shell-rpc-debian-questing`. `release.yml` waits on both Debian jobs. A manual **Release - Debian** run builds plucky only, unless the dispatch gains a suite choice.
- 💩 `⏳` Questing rewrite, before `build-dep`: `libmutter-16` becomes `libmutter-17`, gnome-shell bounds become `>= 49` `<< 50`. Package name stays `gnome-shell-rpc`.
- 💩 `⏳` The two assets on one GitHub Release cannot share a filename. Upload them as `gnome-shell-rpc_<version>_plucky_amd64.deb` and `gnome-shell-rpc_<version>_questing_amd64.deb`. Leave the Debian version inside the package as the changelog version.
- 💩 `⏳` On the questing job, meson follows the installed mutter (`libmutter-17`, `mutter-clutter-17`, `mutter-cogl-17`, `mutter-mtk-17`) and the vendor pin is `49.0`. Shared Vala stays shared. Fork a file only when the 49 GIR or C ABI does not compile. Fix those gaps from the questing build log. Do not pre-build a second copy of every `libmutter-16` source.
- 💩 `⏳` The 25.10 test guest is a new libvirt domain. Leave `ubuntu 25.04_1.qcow` and the domain `ubuntu25.10` as the 25.04 test machine.

**Phase 1 done when:** a Release run has uploaded both debs, and the questing deb has been logged into on an Ubuntu 25.10 virtual machine.

- A rolling `main` vendor build is not part of this plan.
