## Why anyone mentioned `sizeof` / `g_type_query` at all

That pair is **not** “match the API perfectly.” It is a **diagnosis** of one crash class:

1. We compile St against **our** `clutter-actor.h`. `StWidgetClass` embeds `ClutterActorClass parent_class`, so the compiler bakes in **`sizeof(ClutterActorClass)` from that header**.
2. At runtime GObject allocates the parent class using the **registered** `ClutterActor` `class_size` from our stub `.so`.
3. St’s `class_init` then writes slots it cares about (`allocate`, `paint_node`, …). Those writes are at **offsets defined by the header**. If the **allocated** parent class is **shorter** than the header St compiled with, those stores smash → fortify / `g_type_class_get` blow-ups.

So: **whatever we put in the header that St compiles against must fit in the GType we register.** That is memory layout for subclassing, not “implement every Clutter feature.”

Shell does **not** need a complete ActorClass. It needs:

- Types it subclasses to register cleanly.
- The **vfuncs / methods St and Shell actually assign or call** on the boot path.

If the header declares a huge class and the GType is smaller, we can **trim the header** to what we register (boot-minimal), or grow the GType to match the header we already emit. Either is fine; **boot is the gate**.

## What’s going wrong today (symptom, not the product goal)

Generated `ClutterActorClass` header was **448**; Vala registered **440** because `emit_object_class_slots` skipped any field with prefix `parent` — that dropped **`parent_set`** (a real vfunc).

**✔️** Fixed: only skip `parent_class` / `parent`. Actor GType is now **32 / 448** (class matches our header).
