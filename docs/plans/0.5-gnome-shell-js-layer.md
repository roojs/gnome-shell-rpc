## Course correction

**🔷** The product shell is **GNOME Shell JavaScript** (`js/ui`, extensions). This repo does **not** reimplement panel, overview, or Activities in Vala/GTK.

**🔷** We provide a **layer** GJS can run on: mutter keeps compositing; **stock** libgjs; our **typelib + generated stub `.so`** sit first on `GI_TYPELIB_PATH`. GJS `ffi_call`s our symbols; those stubs RPC. No GJS patch.

**🚫** Do **not** patch GJS / `Function::invoke` / `LD_PRELOAD` of GI.

**ℹ️** [`0.3`](0.3-minimal-shell-top-bar.md) fake-shell stays a **throwaway probe**. Do not grow it into the shell.

**🚫** Do not start a Vala overview / hotkey UI as the 0.5 deliverable.

**ℹ️** Early 0.1 text said “Vala first client” and listed “keeping gnome-shell JS as the first client” as out of scope. **That was the divergence.** This plan replaces that target.

## Split (what we replace vs keep)

| Keep (holy grail) | Replace (this repo’s layer) |
|-------------------|-----------------------------|
| gnome-shell **JS** (`js/ui`, `js/misc`, extensions as GJS) | In-process `libgnome-shell.so` **as UI in `MetaPlugin.start()`** |
| Mutter: DRM, Wayland, window actors | In-process GI → libmutter (same address space as GJS) |
| Policy/UX written in JS | A Vala/C **class per Meta type** on the client that wraps RPC |

**Plugin process (already 0.1–0.3):** `gnome-shell-rpc` = libdefault-style effects + `SocketListen` + `Ui` handlers. Completes map/minimize locally.

**Client process (0.5+):** **Stock** libgjs (`gjs-embed`). `GI_TYPELIB_PATH` prepends **our** `Meta-16` (or a toy namespace first). Typelib `shared-library` is our generated stub `.so`. GJS still does `imports.gi.Meta`; C symbols RPC to the plugin. GLib/Gio stay the real typelibs (later on the path).

## Client vs server (do not blur)

**GJS does not run in the plugin.** Two processes:

| | **Client** (GJS process) | **Server** (mutter + plugin) |
|--|--------------------------|------------------------------|
| Runs | Stock libgjs / SpiderMonkey, `js/ui`, our typelib + stub `.so` | DRM/Wayland, real `Meta*`, stage, `SocketListen`, apply ops |
| Crash | Shell JS / GJS / SpiderMonkey die | Compositor / session die |
| Stay up if the other dies | Windows keep painting | Client reconnects or exits; windows stay |

**What out-of-process buys:** kill the shell client → windows stay. That is the holy-grail crash story. We are **not** moving GJS into the plugin.

**What still kills the server:** bugs in mutter/Meta, or in plugin code that touches `Meta*` while handling an RPC. Compositor process was always that crash domain.

**🔷** Do **not** “RPC the whole of GJS onto the server.” Only **allowlisted Meta/Shell-shaped calls** cross the socket. GLib/Gio/Gtk/Json stay **local GI** in the client (no RPC).

**💩** Blind plugin-side `g_function_info_invoke` for every client request **does** widen what a buggy shell call can crash in mutter. Prefer curated handlers (like 0.3 `Ui.Display`) or a hard allowlist + validation. Generic GI re-invoke on the server is a later, explicit risk — not the echo-smoke design.

**ℹ️** Echo smoke: dummy server only prints the call. No mutter. No Meta. Crash target is nowhere near the compositor.

## The St / Clutter problem (must decide before a full port)

Stock GJS is not only `window.minimize()`. Panel and overview are **`St` widgets on mutter’s Clutter stage**.

| Approach | Meaning | 0.5 |
|----------|---------|-----|
| **A — Meta/Shell via GI relay** | `gi-stub-gen` from installed typelibs; stub `.so` RPCs. JS chrome still assumes a local stage | Grow generator + Meta/Shell stubs. Does **not** boot full `js/ui/main.js`. |
| **B — Remote the stage** | Clones, `St`, textures over RPC/dmabuf | Later; overlaps old “overview fds” work. |
| **C — Change js/ui to Wayland chrome** | JS kept, `St`-on-stage abandoned | **Replicating layout** — **🚫** unless the user reopens it. |

**🔷** `⏳` 0.5 is **approach A**: GI-shaped Meta/Shell calls work out of process. Document what still requires a stage and defer that.

**💩** `⏳` Full `js/ui/main.js` boot in 0.5? **No** until A is real and the stage gap is explicit.

## Generate from typelibs (not from JS archaeology)

**🔷** The relay is driven by **installed typelibs** (`Meta-16`, later `Shell`, …) via `gi-stub-gen`. Walk the library with GIRepository; emit stubs. **🚫** Do not start from a gnome-shell `js/` inventory to decide which symbols exist.

**ℹ️** Point `gi-stub-gen` at the typelibs you want to relay (`Meta-16`, later `Shell`, …). Those are separate from `St` / `Clutter` typelibs — you are not generating those unless you ask for them.

**ℹ️** Gio/GLib/Json stay **real** typelibs on the client (not shadowed).

**🚫** Do not hand-write a JS-facing `Remote.Window` tree. Fake-shell `Remote` stays throwaway. **Generated Vala stubs from typelib** (one symbol → RPC) are the client layer.

## What we replace: the typelib’s **shared library**, not GJS

GJS stays stock. It loads `Meta-16.typelib`, `dlopen`s `shared-library`, `ffi_call`s `c:identifier`.

**Wrong:** patch GJS (`Function::invoke`) or `LD_PRELOAD` GI. Thicker, fights an ABI we do not own.

**Right:** our typelib **first** on `GI_TYPELIB_PATH`, `shared-library` = **generated stub `.so`**. Each exported symbol is a thin stub that RPCs (name + args). Same JS: `imports.gi.Meta.window.minimize()`.

```
today:    GJS --GI--> libmutter.so.0
target:   GJS --GI--> our stub .so  --libocrpc--> plugin --> real MetaWindow
          (typelib first on GI_TYPELIB_PATH)
```

**🔷** Schema = typelib (namespace / symbol allowlist as needed for generator maturity). Generator emits **Vala** stubs + typelib pointing at our `.so`. **No Python.**

**🚫** Hand-written `GnomeShellRpc.Remote` for GJS. `Remote` is fake-shell only.

**ℹ️** Gio/GLib/Json stay **real** typelibs (our path only shadows `Meta` / toy namespace).

**ℹ️** GJS still wraps GObjects from our `get_type`. Those types live in the stub `.so`; instance identity for mutter is a lease id inside the stub, not a Vala `Remote.Window` API.

## libgjs (installed: 1.82.1)

**ℹ️** Distro: `libgjs-dev` / pkg-config **`gjs-1.0`**. Public include is `<gjs/gjs.h>` → `context.h`, `coverage.h`, `error-types.h`, `mem.h`, `profiler.h`. Requires.private: `mozjs-128`, `gobject-introspection-1.0`.

**ℹ️** **No VAPI** and **no GIR** for `GjsContext`. (`GjsPrivate-1.0.typelib` under `/usr/lib/.../gjs/girepository-1.0/` is not the embed API.) Vala needs a **small hand vapi** for `Gjs.Context` if we embed from this repo.

Public embed surface (what we can set up without patching):

| API | Role |
|-----|------|
| `gjs_context_new()` / `gjs_context_new_with_search_path()` | Construct; **JS module search path** (`imports.searchPath`) |
| GObject props `search-path`, `program-name`, `program-path`, `profiler-enabled`, `profiler-sigusr2` | Same setup gnome-shell uses |
| `eval` / `eval_file` / `eval_module` / `eval_module_file` / `register_module` | Run our `smoke.js` |
| `define_string_array` / `set_argv` | `ARGV` etc. |
| `get_native_context()` | `JSContext*` (SpiderMonkey) — **not** a GI intercept |
| coverage / profiler / GC / debugger console | Not the 0.5 hook |

**🚫** There is **no public “intercept import” / “intercept GI invoke”** on this API. `gjs_importer_class` / `gjs_repo_class` are exported symbols **without headers** — internal JSClasses, not a supported hook.

**ℹ️** Typelib search is **GIRepository** (`prepend_search_path` / `GI_TYPELIB_PATH`), not `GjsContext` search-path. Search-path is for **JS files**.

**🔷** `✔️` Embed `GjsContext` (`gjs-embed` + `vapi/gjs-1.0.vapi`). Stock libgjs — no fork.

## GIR / typelib first (the layer)

**ℹ️** JS modules: `Gjs.Context` search-path. **GI namespaces:** `GI_TYPELIB_PATH` / `g_irepository_prepend_search_path`. First `Meta-16.typelib` wins. Mutter GIR: `shared-library="libmutter-16.so.0"`.

**🔷** Our typelib first, `shared-library` = generated stub `.so`, every `c:identifier` exported. That *is* simpler than patching GJS: public GI, stock libgjs, `gjs-embed` prepends the path.

**ℹ️** Generator must also emit `*_get_type` (and enough GObject class) for types GJS holds.

## Next smoke: GJS GI invoke → dummy RPC (echo)

**🔷** `✔️` Run **stock** `gjs-embed`. Script uses GI as usual. Our stub `.so` (typelib first) **emits RPC**. Dummy server echoes. No mutter.

The RPC **does not have to reach mutter or succeed**. A **dummy server** that listens and **echoes** (“got this call”, dump method/args) is enough.

That proves the layer: GJS still thinks it is calling GI; the backing `.so` is ours.

**🚫** Not a GJS rewrite of `rpc-client` (hand-calling `OLLMrpc` / `Ui`).
**🚫** Not nested mutter, not fake-shell, not real `minimize` on a window.
**🚫** Not a client class per type.
**🚫** Not “inventory JS then decide symbols.”

**Later:** same generator against the real plugin. Stage chrome (`St`/Clutter) is a separate problem when JS needs it — not this generator step.

## Generator (typelib via GIRepository)

**🔷** Read symbols from the **typelib** (`GI.Repository.require`), not GIR XML. Emit **Vala** wrappers; package with `g-ir-compiler --shared-library=…`.

**🚫** Do not build a full GIR XML parser / include merger.

**🔷** `✔️` `Generator` — emit by `InfoType` (function / object / enum / flags / constant / struct / interface / callback); `Application` is CLI only.
**🔷** `✔️` Callables: utf8→utf8 namespace functions → `Runtime.call_utf8`; others → signature + `GLib.error("… not wired")` for now.
**🔷** `✔️` Meson builds `libgirpcsmoke.so` from generated Vala + hand `Runtime` / `PingParams` / `PingResult`.
**🔷** `⏳` Wire object methods / richer signatures to RPC; constructors; array/`GList` types.

```bash
./build/src/gi-stub-gen emit GiRpcSmoke 1.0 --typelib-dir=./build/src \
  --allow=ping --out=./build/src/GiRpcSmoke_generated.vala

./build/src/gi-rpc-echo --debug
GI_RPC_SMOKE_TYPELIB_DIR=./build/src \
  ./build/src/gjs-embed --debug src/gjs-embed/smoke.js
```
