## Fixed (2026-09-03)

**Cause (confirmed via GDB):** stub `St.Viewport` did not implement `St.Scrollable` (`hadjustment` / `vadjustment`). GJS registers `MessageView` (`Implements: [St.Scrollable]`, extends `St.Viewport`); GObject class setup hit corrupt heap in `g_type_register_static` ← GJS (`musable` / `realloc` before register).

**Fix landed:**

- `src/gi-stub-gen/St.overrides` — `Namespace emit_implements=1` → `Viewport : Widget, Scrollable`
- `src/gi-stub/overrides-st/Viewport.override.vala` — fieldless `hadjustment` / `vadjustment` + `get_adjustments` / `set_adjustments` stubs
- `src/meson.build` — Viewport override in gi-stub-gen inputs

**After fix:**

| Check | Before | After |
| --- | --- | --- |
| `Scrollable` CRITICAL on `MessageView` | every failing run | **gone** |
| `messageList.js` (3× + 13× GDB) | CRITICAL → heap abort | **all OK** |
| `overview.js` (3×) | mixed | **3/3 OK** |
| `components.js` (3×) | mixed | **2/3 OK** — still intermittent |
| `layout.js` (3×) | mixed | **2/3 OK** — still intermittent |
| `panel.js` (3×) | always `realloc(): invalid next size` | **0/3** — separate bug? |

Hypothesis **confirmed for MessageView**; remaining crashes are **not** the same Scrollable-on-Viewport gap (or not only that).

### ASAN notes

Two separate things were conflated in earlier notes:

| When | `detect_leaks=0`? | Why |
| --- | --- | --- |
| **`ninja` / codegen** | **Yes** | `gi-stub-gen` subprocesses under ASAN hit leak-check noise during build; this does **not** apply at runtime. |
| **Runtime repro** | **No** — use normal ASAN options | `build-asan/` + 15+ runs of the smoke: **zero repro**. |

Runtime ASAN did not help here mainly because the aborting frame is in **system `libmozjs-128`**, while only our binaries were built with `-Db_sanitize=address`. ASAN instruments allocations in linked ASAN objects; a heap smash inside non-ASAN mozjs/gjs often shows up only as glibc `realloc`/`double free` (what we see in Track B), not a neat ASAN report pointing at our stub. To get ASAN reports on the JS engine path you would need an ASAN-built mozjs/gjs stack (heavy) or find the bad write on the Vala/RPC side with GDB/Valgrind.

So: we are **not** disabling leak detection to debug this bug — we disabled it **during build** so codegen completes, and runtime ASAN simply **did not reproduce** this intermittent crash in a mixed library setup.
