# valac GIR emits `GLib.DesktopAppInfo` — that type does not exist in GI

**Status:** ⏳ open — blocks overview folder icons / `shouldShowApp(app.app_info)`.  
**Plan:** [`0.8-init-complete-and-interaction.md`](../plans/0.8-init-complete-and-interaction.md)  
**Search row:** [`2026-09-19-overview-app-search-empty.md`](2026-09-19-overview-app-search-empty.md) (Do 5 icons).  
**Hit:** nested 2026-09-19 19:39 — `JS ERROR: Unable to resolve arg type 'DesktopAppInfo'`  
  (`appDisplay.js` `FolderView._loadApps` → `parentalControlsManager.shouldShowApp(app.get_app_info())`).

**Roles:** Vala `--gir` typing for a stock GIO type · **not** a new Shell API · **not** nested-GStrv inject.

## Symptom

GJS loads our `Shell-16` typelib, then calls through to parental controls with a `Shell.App` desktop info:

```js
// vendor/gnome-shell/js/ui/appDisplay.js ~2205
this._parentalControlsManager.shouldShowApp(app.get_app_info())
```

```js
// vendor/gnome-shell/js/misc/parentalControlsManager.js ~130
// Calculate whether the given app (a Gio.DesktopAppInfo) should be shown
shouldShowApp(appInfo) { … appInfo.should_show() … }
```

Same object is also `app.app_info` in `appFavorites.js`. GJS dies:

```text
Unable to resolve arg type 'DesktopAppInfo'
```

Overview **application icons at the top** (folder view / app grid filter) never populate. Search hits can still come back from `AppSystem.search`; this miss is the **GIR type name** on `Shell.App.app_info` / `get_app_info()`, not the search C symbol.

## What is actually true

There is **one** C type:

| Layer | Name |
| ----- | ---- |
| C | `GDesktopAppInfo` (`gio/gdesktopappinfo.h`, `g_desktop_app_info_get_type`) |
| Stock GI / GJS | **`Gio.DesktopAppInfo`** (`Gio-2.0.gir` `<class name="DesktopAppInfo" c:type="GDesktopAppInfo">`) |
| Stock `Shell-16.gir` | `get_app_info` / property `app-info` → `<type name="Gio.DesktopAppInfo" c:type="GDesktopAppInfo*"/>` |
| Vala **code** | `GLib.DesktopAppInfo` — this is normal. Vala puts all of Gio in `namespace GLib` (`GLib.AppInfo`, `GLib.File`, …) |
| valac `--gir` from our `Shell.App` | **`GLib.DesktopAppInfo`** — this is **not** a GI type |

`GLib-2.0.gir` has **no** `DesktopAppInfo`. The only typelib GJS can load that type from is **Gio-2.0**. Unqualified `DesktopAppInfo` in a Shell method signature is supposed to mean `Gio.DesktopAppInfo` (Gio is already `<include>`d). When valac writes `GLib.DesktopAppInfo`, GI looks for a class that does not exist.

`GLib.AppInfo` does **not** have this bug: valac emits `Gio.AppInfo`, which matches Gio-2.0.

---

## Why valac does this

Distro vapis (`vala-0.56` here):

**`gio-2.0.vapi`** — Gio types live in Vala `GLib`, but GIR is told they are Gio:

```vala
[CCode (cprefix = "G", gir_namespace = "Gio", gir_version = "2.0", lower_case_cprefix = "g_")]
namespace GLib {
    public interface AppInfo : GLib.Object { … }
```

**`gio-unix-2.0.vapi`** — same Vala namespace, **no** `gir_namespace`:

```vala
/* gio-unix-2.0.vapi generated by vapigen, do not modify. */
[CCode (cprefix = "G", lower_case_cprefix = "g_")]
namespace GLib {
    [CCode (cheader_filename = "gio/gdesktopappinfo.h")]
    public class DesktopAppInfo : GLib.Object, GLib.AppInfo {
```

`DesktopAppInfo` is unix-only, so vapigen put it in `gio-unix-2.0.vapi` instead of `gio-2.0.vapi`. GirWriter takes `gir_namespace` from the **namespace declaration that owns the type**. For `AppInfo` that is Gio. For `DesktopAppInfo` that attribute is missing, so the GIR name is the Vala namespace: `GLib.DesktopAppInfo`.

The rest of `gio-unix-2.0.vapi` is the same hole (`UnixInputStream`, `UnixFDList`, …). Those are also `Gio.*` in `Gio-2.0.gir`. We only explode today because **Shell GIR exports `DesktopAppInfo`**.

Vala source still uses `GLib.DesktopAppInfo`. That part is **correct** (same pattern as `GLib.AppInfo`). The bug is **GIR output**, not the Vala identifier in `App.vala`.

## Rejected: `vapi/gio-desktopappinfo.vapi` (`Gio.DesktopAppInfo : GLib.DesktopAppInfo`)

Tried as a “trivial” local binding:

```vala
[CCode (cprefix = "G", gir_namespace = "Gio", gir_version = "2.0", lower_case_cprefix = "g_")]
namespace Gio {
    [CCode (cname = "GDesktopAppInfo", type_id = "g_desktop_app_info_get_type ()")]
    public class DesktopAppInfo : GLib.DesktopAppInfo {
        public DesktopAppInfo (string desktop_id);
    }
}
```

plus `--pkg=gio-desktopappinfo` on `shell-gi` and on `gnome-shell-rpc` because `shell-gi-16.vapi` then mentioned `Gio.DesktopAppInfo`.

That is the wrong layer.

1. **Same GType, fake inheritance.** `GDesktopAppInfo` is not a subclass of `GDesktopAppInfo`. The vapi tells Vala there are two classes. There is one.

2. **Fights the Vala Gio model.** Every other Gio type is `GLib.Foo` in Vala and `Gio.Foo` in GIR. Inventing a Vala `Gio.DesktopAppInfo` means `App.vala` and `AppSystem.vala` disagree (`Gio.*` vs `GLib.*`), and every `--pkg=shell-gi-16` consumer must also `--pkg` a package that is not pkg-config, not Gio, and not unix.

3. **Duplicates the constructor** (`g_desktop_app_info_new`) already on `GLib.DesktopAppInfo`. Any further method we copy is a second, drifting binding of the same class.

4. **Does not fix `gio-unix-2.0.vapi`.** Anything still typed `GLib.DesktopAppInfo` (casts from `GLib.AppInfo.get_all()`, docs, other libraries) still GIR-emits `GLib.DesktopAppInfo`.

5. **Would lie in our own GIR if valac emitted a new class** rather than only rewriting the type *name* on `Shell.App.app_info`. A second `DesktopAppInfo` class in `Shell-16.gir` or a Gio class that is not Gio-2.0’s class is worse than the original miss.

User (2026-09-19): GIR inject was the wrong way; this vapi is wrong as well. **Do not** put it back. **Do not** switch `Shell.App.app_info` to a made-up `Gio.DesktopAppInfo` Vala type.

## What a real fix looks like

Keep Vala source as **`GLib.DesktopAppInfo`**. Make valac `--gir` write **`Gio.DesktopAppInfo`**, the way it already writes `Gio.AppInfo` for `GLib.AppInfo`.

That is **one metadata attribute** on the unix vapi’s `namespace GLib` (or whatever GirWriter actually keys off per type in that file):

```vala
[CCode (cprefix = "G", gir_namespace = "Gio", gir_version = "2.0", lower_case_cprefix = "g_")]
namespace GLib {
    public class DesktopAppInfo : GLib.Object, GLib.AppInfo {
```

Honest ways to get that attribute into the compile:

| Approach | What it is |
| -------- | ---------- |
| Shadow **`vapi/gio-unix-2.0.vapi`** on our `--vapidir` (copy of distro file, **only** add `gir_namespace = "Gio"` on that namespace) | Same types, same C names. Meson already prefers `vapi/`. Ugly because it vendors the whole unix vapi, but it is not a new class. |
| Upstream Vala / vapigen | `gio-unix-2.0.vapi` should get the same `gir_namespace = "Gio"` as `gio-2.0.vapi`. Distro file says generated, do not modify. |

A four-line “empty `namespace GLib { }` with `gir_namespace = Gio`” overlay is **not** assumed to work: GirWriter appears to honour the namespace CCode on the **file that declared the class**, and slapping `gir_namespace` on merged `GLib` globally would be a footgun for `GLib.Object`. Prove it before relying on it.

**Success:** `build/src/Shell-16.gir` (vala_gir, **before** inject) has `name="Gio.DesktopAppInfo"` on `App.app-info` / `get_app_info`, and **no** `GLib.DesktopAppInfo`. `App.vala` still says `GLib.DesktopAppInfo`. No extra `--pkg`. Nested: no `Unable to resolve arg type 'DesktopAppInfo'` on folder load / `shouldShowApp`.
